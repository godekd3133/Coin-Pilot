# Coin Pilot 제품 기획서

> 기준일: 2026-09-23. 현재 저장소의 코드와 기존 문서를 대조해 정리한 기준 문서입니다. 기능 상태는 `구현 확인`, `계획`, `검증 미완료`로 구분합니다. 코드 구현 확인은 실제 운영, 단말 동작, 전략 수익성 검증 완료를 뜻하지 않습니다. 스펙은 제품이 확장되면서 이 문서와 기능별 상세 스펙에 누적합니다.

## 1. 제품 개요

**Coin Pilot의 최종 목표는 규칙에 따라 자동매매를 수행해 거래 비용과 손실을 반영한 실제 순이익을 내는 것이다.** 이를 위해 전략을 발굴하고, 같은 시장 데이터를 이용해 비교하고, 과거 검증과 별도 보유 구간 검증, 단일 실행 주체의 모의 선행 운용, 소액 실거래의 체결·계좌 정산 확인을 차례로 거쳐 자본 확대 여부를 판단한다. 이 목표는 아직 달성된 성과를 뜻하지 않는다. 현재 전략의 수익성은 별도 증거로 확인해야 하며 수익을 보장하지 않는다.

Coin Pilot은 업비트 계정의 시장 정보, 규칙 기반 자동매매, 전략 연구, 주문·체결·정산 기록을 한곳에서 다루는 개인용 운용 도구다. 앱의 핵심 가치는 전략 후보를 실제 운용 판단에 필요한 증거까지 추적하고, 손실이나 데이터 이상이 생기면 정해 둔 규칙에 따라 신규 진입을 멈추는 데 있다.

현재 제품은 단일 기능의 매매 봇이 아니라 다음 세 영역을 가진다.

1. **운용 화면**: 잔고·포지션·시장·분석·뉴스를 확인하고 수동 주문을 수행한다.
2. **자동매매 런타임**: 기본 모의 실행에서 전략 신호와 포지션 위험을 관리하며, 실주문은 별도 설정과 게이트가 필요한 위험 영역이다.
3. **전략 연구·검증**: 백테스트, paper forward, shadow 관측과 실거래 evidence를 분리해 후보를 평가한다.

## 2. 목표와 비목표

### 제품 목표

- 시장 상태, 계좌 상태, 봇 상태, 주문 상태를 한 대시보드에서 읽을 수 있게 한다.
- 사람이 거래를 수행하거나 자동 실행을 관찰할 때 현재 모드와 거래 위험을 명확히 보여준다.
- 전략 변경은 과거 데이터, 분리된 모의 관측, holdout 등 적절한 근거로 평가하고, 승격 여부를 명시적으로 관리한다.
- 후보 발굴부터 실거래 규모 결정까지 각 단계를 통과한 규칙 기반 전략으로 비용 차감 후 순이익을 추구한다.
- 신호·주문 접수·체결·계좌 readback을 구분해 수익과 손실을 실제 관측값에 근거해 기록한다.
- 모바일 및 설치형 웹앱에서도 동일한 서버 상태를 안전하게 조회할 수 있게 한다.

### 비목표

- 수익률 보장, 손실 방지 보장, 투자 권유 또는 거래소 서비스를 제공하지 않는다.
- 과거 백테스트나 소수의 paper 거래만으로 전략이 수익성 있다고 주장하지 않는다.
- AI 의견을 주문으로 자동 변환하지 않는다.
- 현재 확인되지 않은 기능을 로드맵에 적혀 있다는 이유만으로 출시된 기능처럼 안내하지 않는다.

## 3. 사용자와 주요 과업

**주 사용자**는 업비트 계정을 직접 관리하며 자동화 도구를 실험하는 개인 운영자다. 전략 연구자는 과거/forward 자료를 비교하고 후보의 데이터 품질과 실행 비용을 확인한다. 모바일 사용자는 같은 LAN 또는 설정된 접속 환경에서 봇과 포트폴리오 상태를 빠르게 관찰한다.

대표 과업:

- 현재 앱이 DRY_RUN인지 LIVE인지 확인하고 시장과 포지션 상태를 본다.
- 수동 매수·매도 또는 설정된 자동 전략을 사용하되, 주문 결과와 실제 체결을 따로 확인한다.
- 신호가 발생하지 않는 이유, 데이터 지연, risk heartbeat 중단 등 운영 상태를 진단한다.
- 후보 전략의 백테스트와 paper/shadow evidence를 비교하고 승격 조건 충족 여부를 판단한다.
- AI 자문 및 뉴스·시장 분석을 참고하되 이를 확정적 신호로 취급하지 않는다.

## 4. 핵심 가치와 제품 원칙

1. **관측 가능한 상태**: 수치뿐 아니라 시점, 데이터 품질, 실행 모드, 출처를 함께 표시한다.
2. **모드의 명확성**: DRY_RUN, paper/shadow research, LIVE 주문을 별도 플로우와 라벨로 유지한다.
3. **실패 시 안전 정지**: 오래된 시세, 분석 공백, 리스크 모니터 단절, 체결 evidence 저장 실패 등 신뢰할 수 없는 상태에서는 진입이나 후속 주문을 제한한다.
4. **근거 없는 승격 금지**: 연구 lane은 명시적으로 승격되기 전까지 연구 전용으로 남는다.
5. **실제 결과 우선**: 주문 접수는 체결이 아니며, 체결은 계좌 정산 확인과 다르다.
6. **사람이 결정**: AI 권고, 파라미터 최적화, 후보 점수는 판단 보조 자료다.

### 핵심 사용자 플로우

```text
앱 접속 → 인증/연결 상태 확인 → 모드(DRY_RUN/LIVE) 확인
   ├─ 관찰: 시장·분석·뉴스 → 계좌·포지션·거래 evidence 확인
   ├─ 수동 거래: 금액·시장·주문 확인 → 실행 → 접수 결과 → 체결/정산 readback
   ├─ 자동 운용: 설정·데이터 건강 확인 → 신호 → 지연 후 재검증 → 위험 게이트
   │              → paper 기록 또는 LIVE 주문 → fill evidence → 포지션/청산 관찰
   └─ 연구: 과거 검증 → 격리 paper/shadow → forward/holdout 평가 → 명시적 승격 검토
```

각 화면은 “값이 없음”, “오래됨”, “관측 불가”, “차단됨”을 정상값이나 0으로 바꾸지 않고 구별해야 한다. LIVE 거래 플로우에서 부분 fill 또는 fill 미관측은 완료 거래로 집계하지 않아야 한다.

수동 주문 경로와 자동 스캘핑의 live validation gate는 서로 다른 기능이다. 거래 화면의 수동 단일 주문과 스마트 매수·매도 API가 있다는 사실만으로 자동 스캘핑 전략이 LIVE 승격됐다는 뜻은 아니다. 현재 `MultiCoinTrader.validatePromotionReport`는 `fixed_config`, 전략 모드와 마켓, 현재 runtime 설정 일치, 통계 신뢰도 게이트 및 `promoted=true`를 검사하지만 보고서 생성 시점의 24시간 freshness를 강제하지 않는다. `assessScalpingValidationReportFreshness`는 API 응답에 보고서 시점의 신선도를 표시하는 용도다. `requireValidationPassForLive=false`이면 자동매매 시작 시 promotion report gate 검사 자체를 건너뛸 수 있으므로 실제 설정도 함께 확인해야 한다. 따라서 보고서의 시점과 실제 LIVE gate 판정은 구분해 읽어야 한다.

읽기 전용 `GET /api/strategy-readiness`는 구현되어 있다. 응답의 `liveGate`는 실제 promotion validator 결과와 LIVE 적용 여부를 나타내며 `enforcedFreshness=false`로 보고서 나이가 LIVE gate의 강제 조건이 아님을 명시한다. `report.freshness`와 `currentEvidence`는 현재성 판단을 별도로 나타내므로, 오래된 보고서는 `liveGate.passed=true`일 수 있어도 readiness 상태는 `BLOCKED`가 된다. route 테스트는 설정 보고서의 정상·누락·손상·오래됨·미래 시각, runtime 설정 불일치 및 validator 부재를 확인한다. `READY`는 현재 검증 증거를 읽을 수 있다는 뜻일 뿐, 실거래 순이익이나 전략의 지속적인 수익성을 증명하지 않는다.

준비 화면과 API의 세부 필드 연동은 아직 안정적으로 확인되지 않았다. 화면에서 보고서 파일명·생성 시각·freshness·gate 적용 여부·차단 이유를 구분해 보여주는 상세 표시를 우선순위 1의 후속 작업으로 둔다. 이 표시가 구현되고 검증되기 전까지 화면 연동 상태는 `부분 구현 / 검증 미완료`다.

## 6. 운용 원칙과 중단 조건

- **기본 모드**: `DRY_RUN=true`를 기본으로 유지한다. LIVE 전환은 별도 운영 결정이며 단순 UI 설정/AI 의견/최적화 결과로 암묵적으로 일어나면 안 된다.
- **시장 데이터**: stale candle, 부족한 캔들, 분석 coverage gap은 별개 상태로 기록한다. 불완전한 입력에서 신규 진입을 fail-closed 한다.
- **포지션 보호**: risk ticker는 시장 분석 부하와 독립적으로 정상성·연속성을 감시한다. 오랫동안 성공 관측이 없으면 신규 운용을 막는다.
- **주문과 결과**: `ORDER_SUBMITTED`는 체결을 뜻하지 않는다. executed volume, 평균 가격, 수수료 등 확인 가능한 exchange fill만 체결 evidence로 기록한다. 계좌 readback 없이는 wallet settlement를 관측했다고 표시하지 않는다.
- **연구 분리**: backtest, deterministic dashboard mock, paper forward, shadow, staging, LIVE fill은 서로 대체 가능한 근거가 아니다. 각 결과는 lane과 기간, 표본 수를 동반한다.
- **AI와 최적화**: 권고와 파라미터 후보는 설명 가능한 참고 자료다. 실행 변경과 전략 승격을 자동 승인하지 않는다.
- **자격 증명·대시보드**: 거래소 secret을 클라이언트에 노출하지 않는다. 현재 `DASHBOARD_TOKEN`이 없으면 auth 모듈이 loopback bind를 강제하고, 토큰이 있으면 설정된 LAN 접근 정책을 사용한다. CORS/origin 검사와 TLS 관련 경로도 코드에 있다. 실제 외부 배포 보안은 배포 설정에서 별도 확인한다.
- **오프라인**: PWA 캐시는 shell 용도다. 오래된 계좌/시세 값으로 신규 주문을 가능하게 만들지 않는다.

## 7. 수익 목표, 성과 지표와 판단 기준

최종 성과는 **실제 체결과 계좌 잔고 변화를 대조해 확인한 비용 차감 후 순이익**이다. 총수익이나 승률만으로 성공을 판정하지 않는다. 손실 통제, 기준선 대비 성과, 체결 품질, 데이터·운영 연속성도 함께 본다. 손익 결과는 실현 손익과 미실현 손익을 나누고, 거래소 수수료·호가 차이·슬리피지·취소 및 재주문 비용을 반영한다. 자본 투입·회수, 입출금, 미체결 주문을 손익과 혼동하지 않는다.

### 전략 검증 및 자본 확대 플로우

| 단계 | 수행 내용 | 통과 기준 | 탈락·중단 조건 / 상태 |
|---|---|---|---|
| 1. 전략 발굴 | 시장 가설, 진입·청산·포지션 크기·손실 제한 규칙을 명시하고 기존 기준 전략을 둔다. | 규칙을 데이터만으로 재현할 수 있고, 미래 정보 참조와 중복 신호가 없다. | 설명할 수 없는 규칙, 사후적으로만 만든 조건, 누락된 데이터 계약은 후보에서 제외한다. |
| 2. 동일 데이터 비교 | 후보와 기준 전략을 같은 마켓·기간·시세 snapshot·초기 자본·체결 모델로 비교한다. forward variant 비교는 공통 snapshot을 각 격리 장부에 공급한다. | 설정과 데이터가 일치하고, 후보별 독립 장부·비교 보고서가 남는다. | 서로 다른 창, 시장 구성, 설정의 손익은 합산하지 않는다. 설정 drift나 누락 snapshot은 비교 무효다. |
| 3. 비용 반영 백테스트 | 수수료, spread/슬리피지, 지연 및 체결 가능성을 반영하고 구간별 walk-forward로 점검한다. | 순수익, 손익비/수익인자, 최대 낙폭, 거래 수, 시장 국면별 결과가 사전 기준을 만족한다. | 비용 차감 후 기대 순이익이 0 이하이거나 낙폭·체결 가정이 허용 범위를 넘으면 탈락 또는 재설계한다. |
| 4. 독립 holdout | 튜닝에 쓰지 않은 기간·마켓 구간에서 잠근 설정을 검증한다. 보고서가 승격 가능을 표시하더라도 이 단계만으로 실거래 수익을 주장하지 않는다. | 사전 등록한 표본·기간 조건을 충족하고 기준선 대비 순성과가 양수이며 낙폭 한도와 데이터 품질 조건을 만족한다. | holdout을 열어본 뒤 규칙을 바꾸면 새 holdout이 필요하다. 미통과, 표본 부족, 불연속 데이터는 보류 또는 탈락이다. |
| 5. 단일 owner 모의 선행 운용 | 한 개의 owner 프로세스가 잠긴 설정으로 격리 paper 장부를 운영한다. 동일 프로세스가 소유한 장부만 평가하고 shadow·진단 장부를 엄격 모의 손익에 섞지 않는다. | 현재 보고서의 최소 기간·거래 수, 연속성, 설정 고정, 미청산 포지션 0, 비용 차감 순손익·신뢰도 조건을 모두 통과한다. 기준 수치는 `.env.example`과 해당 보고서의 유효 설정에서 읽는다. | owner 중복, heartbeat 단절, 설정 drift, 시세/호가 품질 실패, 미청산 상태, 순손실 또는 기준 미달이면 관측을 중단·무효화하고 원인 수정 뒤 새 격리 세션으로 다시 시작한다. |
| 6. 소액 실거래 체결·정산 검증 | 별도 운영 결정 이후 제한된 작은 규모로 주문을 내고 거래소 주문·부분 체결·수수료·잔고 readback을 대조한다. 자동 전략 승격은 기존 live gate와 설정을 확인한다. | 모든 주문의 체결 수량·평균가·수수료가 조회되고, 거래 전후 잔고와 장부가 조정 가능하며, 실현 순손익이 사전 손실 한도 안에 있다. | 체결 미확인, 미해결 주문/evidence, 계좌 불일치, 비용 모델 오차, 손실 한도 도달 시 신규 주문을 멈추고 원인을 해결한다. |
| 7. 자본 확대 판단 | 여러 운용 구간의 실거래 정산 결과와 비용·낙폭·시장 국면·가동 중단 이력을 검토한다. | 실현 순이익과 손실·낙폭·체결 품질이 사전 기준을 만족하고, 더 큰 주문의 유동성과 체결 비용을 별도로 감당할 근거가 있다. | 결과가 불안정하거나 구간별 편차·비용·낙폭이 커지면 증액하지 않고 현재 규모 유지, 감액 또는 중단한다. |

이 순서는 현재 완료 상태를 선언하는 것이 아니라 제품이 목표로 하는 판단 플로우다. 각 gate는 데이터 기간, 코드·설정 식별자, 마켓 구성, 비용 가정, 표본 수, 보고서 경로, 판정 시각을 보존한다. 실제 계좌의 체결·정산이 확인되지 않은 단계에서는 앱의 수익 목표가 달성됐다고 기록하지 않는다.

### 현재 위치

저장소의 자동매매·연구·체결 증거 기능은 코드에 구현되어 있지만, 자동 전략이 비용 차감 후 순이익을 내고 있다는 점, 실제 거래소 정산으로 결과가 검증됐다는 점, 자본을 확대해도 된다는 점은 아직 입증되지 않았다. 현재 루트 `scalping_validation.json`은 **2026-09-13 생성, `fixed_config`, BTC·ETH·XRP, `promoted=false`**인 과거 검증 기록이다. 이 파일은 생성 당시 설정의 판정만 보여 주며 현재 시장 상태나 실행 중인 런타임의 최신 결과를 나타내지 않는다. 따라서 현 위치는 실거래 수익 검증 및 증액 단계 이전이며, 최신 판정은 새 세션을 임의로 시작하지 말고 당시 기록된 세션·장부·보고서를 확인해 갱신한다.

### 수익·위험 지표

| 지표 | 판단 목적 | 사용 원칙 |
|---|---|---|
| 실현 순손익 / 순수익률 | 실제 닫힌 거래가 비용 후 남긴 금액 | 거래소 fill과 계좌 readback으로 대조한다. 원화와 비율, 평가 기간을 함께 기록한다. |
| 미실현 손익 및 순자산 | 열린 포지션을 현재 가격으로 평가 | 실현 손익과 별도 표시하며 승격 판단에서 청산 실적으로 대체하지 않는다. |
| 최대 낙폭 및 손실 연속성 | 자본 감소 폭과 손실 집중 위험 | 전체와 구간별 수치를 함께 보고 사전 한도 초과 시 중단한다. |
| 수익인자·거래당 순기대값·승률 | 수익 분포와 전략의 거래 특성 | 표본 수와 신뢰구간을 같이 본다. 승률 단독으로 승격하지 않는다. |
| 기준선 대비 순성과 | 단순 보유 또는 승인된 기본 전략 대비 추가 가치 | 동일 기간·자본·비용·마켓 구성에서 비교한다. |
| 체결 오차와 비용 | 가정 체결가 대비 실제 체결 차이 및 총비용 | paper에서 과소 추정된 비용은 전략 재평가와 규모 축소 사유다. |
| 데이터 품질·연속성 | 결과의 유효성과 재현 가능성 | stale, 누락, heartbeat 단절, 설정 변경 구간을 보존하고 부적격 구간을 성공 표본에 포함하지 않는다. |

수치 기준은 전략별 상세 스펙과 현행 설정에서 정하고 변경 이력을 남긴다. API에 이미 존재하는 최소 기간·거래 수·95% 신뢰 하한·양수 실현 손익·미청산 0 조건은 해당 연구 기능의 gate 근거로 사용하되 앱 전체의 영구 기준으로 고정하지 않는다.

| 지표 | 정의/방향 | 기능 수용 기준 |
|---|---|---|
| 상태 출처 표시율 | 핵심 금융·봇 숫자 중 모드 및 최근 관측 시점이 표시된 비율 | 계좌, 포지션, 시세, 거래 결과에 출처/시각/상태가 빠지지 않음 |
| 차단 사유 가시성 | 자동 진입 차단을 원인 코드와 함께 설명하는 비율 | freshness, insufficient candles, analysis gap, risk stale 등의 구분이 UI/API evidence에 보존됨 |
| 체결 분류 정확성 | 접수/미체결/부분·완전 체결/정산 미확인을 구분하는지 | 미관측 값을 fill 또는 settlement로 과장하지 않으며 evidence 손상 시 fail-closed |
| 세션 연속성 | 예정치 대비 heartbeat/data coverage와 재시작 후 ledger 연속성 | 중단을 감추지 않고 interruption으로 기록하며 유효 표본 적격성과 분리 |
| 모드 안전성 | DRY_RUN/LIVE 경계가 UI·API·저장 데이터에서 일치하는지 | 잘못된/불명 모드에서 주문 불가; LIVE 전환과 주문에 명시적 사전조건 필요 |
| 연구 재현성 | 설정 snapshot, 데이터 기간, 비용 가정 및 후보 결과의 재현 가능성 | 연구 결과마다 config/data/version/분할/비용이 기록되고 promoted 상태가 명시됨 |
| 가용성·복구 | 정상 운영 시 API readiness, 복구 후 관측 가능성 | health/readiness 정의 및 재시작·백업·복원 절차가 배포별로 검증됨 |

**연구 수용 기준**: 성과 비교는 비용 반영 후, 분리된 기간 또는 holdout과 적절한 기준선/benchmark를 포함해야 한다. 표본이 작거나 데이터 품질이 나쁘면 결론을 `미확정`으로 둔다. 실거래 전략의 수익성 주장은 장기간의 관측된 체결과 계좌 정산, 손실·비용·시장 국면 분석이 없으면 하지 않는다. 구체 수치 임계값은 전략별 스펙에서 데이터와 운영 목적을 근거로 정한다.

## 8. 확장 방향

아래 항목은 기획상 확장 축이다. 이미 구현된 항목은 기능 구조 표에서 따로 표시했으며, 세부 범위·우선순위는 후속 개발 스펙에서 합의한다.

- **운영 신뢰성**: dashboard 보안·접속 제어, health/readiness, 구조화 로그와 데이터 보존, 재현 가능한 배포 및 복구.
- **정보 밀도 개선**: 봇 상태, 최근 데이터 건강, 주문 lifecycle, 차단 이유 및 증거 lane을 한눈에 비교하는 운영 홈.
- **연구 워크플로**: 후보/기준선 비교, 설정 snapshot, 데이터·비용 가정, holdout·forward 진행 상태 및 승격 근거의 한 화면 관리.
- **계좌·거래 정합성**: exchange order/fill과 계좌 잔고·포지션을 안전하게 대조하고 미해결 상태를 운영자에게 알림.
- **전략 확장**: 새로운 시장 국면/타임프레임/실행 모델을 기존 전략과 격리해 평가하고, 승격 시에만 runtime 설정으로 이동.
- **모바일 설치 경험**: PWA 연결·오프라인·버전 갱신 플로우를 실제 브라우저와 단말에서 검증.
- **AI 자문 품질**: 출처·시점·불확실성·사후 평가를 보존하고, 조언과 자동 실행 사이 경계를 계속 유지.

## 9. 다음 우선 검증·개발 순서

아래는 최종 목표에 직접 기여하는 우선순위다. 상태를 `구현 확인`, `계획`, `검증 미완료`로 기록하며 실제 검증 전에는 완료로 올리지 않는다.

1. **준비 화면의 gate와 보고서 세부 정보 통합 (부분 구현 / 검증 미완료)** — `GET /api/strategy-readiness`는 route 테스트를 포함해 구현 확인 상태다. 후속으로 화면에서 보고서 파일명·생성 시각·freshness, 실제 LIVE gate 적용 여부와 결과, 설정 불일치 등 차단 이유를 구분해 안정적으로 표시하고 화면 연동을 검증한다. 현재 gate는 freshness를 강제하지 않으므로 화면도 freshness를 실제 LIVE gate 통과 조건처럼 표시하지 않는다. 이후 forward 보고서와 연구 route를 연결해 실제 순이익 판단에 필요한 증거까지 추적한다.
2. **동일 데이터 후보 비교와 비용 모델 완성** — 공통 snapshot, 고정 설정, 격리 장부로 기준 전략과 후보를 비교하고 실제 spread/수수료/지연에 맞춰 백테스트 가정을 보정한다. 후보 결과가 runtime 설정에 자동 반영되지 않게 한다.
3. **독립 holdout 및 단일 owner 모의 플로우** — 연구 재현성, 보고서/ledger 추적, 연속성·설정 drift·미청산 포지션 차단을 제품에서 관리한다. 현재 모의 표본의 유효성은 실행 중인 owner와 최신 ledger/report를 조회해 판정한다.
4. **실거래 정산 증거 화면** — 주문 접수, 부분/완전 체결, 수수료, 잔고 대조 및 미해결 evidence를 거래 단위로 연결한다. 자동 스캘핑 승격은 수동 주문 기능과 별도 gate로 유지한다.
5. **소액 검증 이후 자본 확대 판단 도구** — 검증된 실현 손익·최대 낙폭·비용·체결 오차·기준선 대비 결과를 기간별로 보여주고, 사전 손실 한도 도달 시 신규 진입 중지를 우선한다. 증액은 별도 근거와 운영 판단이 확보되기 전까지 후보 상태로 둔다.

## 10. 기능 스펙 추가 템플릿

각 신규 기능은 아래 내용을 채우고, 이 문서의 상태표 및 확장 방향과 연결한다.

```markdown
### [기능명] — [제안 | 승인 | 구현 중 | 구현 확인 | 보류]
- 문제/사용자 과업:
- 대상 사용자 및 사용 상황:
- 기대 결과와 측정 지표:
- 범위 / 명시적 제외 범위:
- 진입 조건과 사용자 플로우:
- 입력 데이터·출처·freshness:
- 동작 규칙과 상태 전이:
- 오류·중단·복구 동작:
- 주문/자금/개인정보 위험 및 fail-closed 조건:
- 연구/DRY_RUN/LIVE 적용 범위:
- 수용 기준과 검증 lane:
- 관련 API·UI·저장 데이터:
- 출시·롤백·운영 관측:
- 결정 사항 / 미해결 질문:
- 근거 링크와 최종 갱신일:
```

### 스펙 변경 원칙

1. `구현 확인`은 코드·UI/API 경로로 확인한 사실만 표시한다. 동작 검증이 필요한 내용은 `검증 미완료`로 둔다.
2. 구현, 실험 계획, 배포, 사용자별 활성화 상태를 서로 다른 상태로 기록한다.
3. 요구사항은 사용자 문제, 관측 가능한 결과, 수용 기준과 검증 방법을 함께 가진다.
4. 금융 수치에는 단위·시점·출처·비용 포함 여부를 붙인다. 작거나 편향된 표본에서 성과 일반화를 하지 않는다.
5. LIVE 경계, 데이터 신선도, 손실 통제, evidence 무결성은 명시적 검토 없이 완화하지 않는다.
6. 변경 시 문서 내 해당 기능 행과 상세 스펙을 같이 갱신하고 변경 근거/상태를 남긴다. 완료된 내용도 검증 lane을 함께 기록한다.
